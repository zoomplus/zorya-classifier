# План реализации MCP-пакета `zorya-classifier-mcp`

## Область и текущее состояние

Владелец выбрал последовательность **сначала MCP поверх текущей библиотеки**, а проверку H8a продолжать отдельно. Это решение заменяет прежнюю зависимость «сначала пройти H8a quality gate, затем начинать MCP». Оно не означает, что H8a прошёл проверку качества, что новый кандидат выбран или что библиотека гарантирует повышение точности.

Цель — отдельный пакет `zorya-classifier-mcp` версии `0.1.0`, использующий опубликованную библиотеку `zorya-classifier` версии `0.2.3` без миграции её публичного API. В пакете закреплены `@modelcontextprotocol/node@2.1.2`, `@modelcontextprotocol/server@2.4.0`, `@modelcontextprotocol/server-legacy@2.4.0`, клиент `@modelcontextprotocol/client@2.4.0` для проверок и `zod@4.2.0`; адаптер `@modelcontextprotocol/node@2.1.2` указывает peer dependency `@modelcontextprotocol/server@^2.4.0`. Библиотека продолжает использовать собственную Zod 3. Рабочая среда пакета — Node.js не ниже `22.12.0`.

### Проверенные факты

- Публичный API библиотеки предоставляет `createClassifier`, обычные OpenRouter vision/text и OpenAI-compatible адаптеры, native decisions и явно внедряемые порты. Конфигурация провайдера, модели и `DecisionPort` остаётся ответственностью вызывающей стороны.
- Библиотека поддерживает обычные vision-language модели без native classifier API. Native decisions остаются отдельным явно сконфигурированным маршрутом.
- Для extraction нужен явно предоставленный caller-owned segmenter и необходимые ему локальные runtime/assets. Пакет MCP не выбирает провайдера, модель или веса и не загружает их автоматически.
- Официальные материалы MCP TypeScript SDK v2, authorization, stdio, HTTP и legacy-клиентов, а также OpenAI custom MCP server, authentication и file reference были проверены главным оркестратором. Per-request SDK server нельзя использовать как хранилище долгоживущих заданий: runtime заданий должен жить отдельно от конкретной протокольной сессии.
- Поддержка MCP-клиентом или SDK-тестом не доказывает наличие аккаунта, deployment или пользовательский интерфейс в стороннем продукте. Такие платформенные пункты остаются `UNVERIFIED`, пока не получено прямое свидетельство.

### Допущения и нерешённые решения

- Точный provider/model для запуска задаёт владелец сервера; значения в документации и примерах являются примерами явной конфигурации, не значениями по умолчанию.
- Способ хранения BYOK-секретов выбирает оператор развёртывания: приватное шифрованное хранилище либо явно включённый режим только в памяти. Поведение после перезапуска описывается согласно выбранному режиму.
- Для автоматических проверок задаётся контролируемый OIDC issuer; проверка входа в конкретный аккаунт ChatGPT и production deployment не выполняются этими тестами и фиксируются отдельно при rollout.
- У владельца уже есть авторизация на согласованную работу и публикацию; этот план не вводит повторный запрос разрешения. Публикация выполняется после подготовки проверяемого пакета и обязательных gates, с учётом возможного шага подтверждения личности на стороне реестра. Внешнее production-развёртывание и ручная проверка пользовательского интерфейса ChatGPT — отдельные rollout-проверки.

## Целевая архитектура и контракты

`zorya-classifier-mcp` — отдельный адаптерный слой. Фабрика получает явные зависимости библиотеки, конфигурацию, principal аутентифицированного запроса и абстракции ввода/хранения файлов. Слой протокола валидирует входы Zod-схемами, проверяет доступ и передаёт типизированную команду в общий runtime. Runtime создаёт серверные задания, применяет общий абсолютный deadline, лимиты очереди и байтов, координирует отмену и вызывает библиотеку через её публичные интерфейсы. Результаты и ошибки переводятся в стабильные tool/job-контракты. Пакет не выбирает провайдера, модель, сегментатор или секрет.

Шесть обязательных инструментов:

| Инструмент           | Назначение и контракт                                                                                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `zorya_classify`     | Классификация изображения по явно заданной конфигурации и закрытым идентификаторам результата. Не изобретать вероятности из ранжированного ответа.                            |
| `zorya_locate`       | Локализация в координатах источника. Сетка, грубая область и bbox не выдаются за маску сегментации или целый объект.                                                          |
| `zorya_extract`      | Извлечение видимой маски через явно предоставленный сегментатор. Нужны caller-owned assets/runtime; корректный результат маски строится только из проверенных пикселей маски. |
| `zorya_get_job`      | Чтение принадлежащего тому же principal задания, его состояния, типизированной ошибки или результата.                                                                         |
| `zorya_cancel_job`   | Запрос отмены задания его владельцем. Ресурсный слот удерживается, пока физическая операция не завершится.                                                                    |
| `zorya_capabilities` | Описание настроенных операций, транспортных возможностей, лимитов и доступных входов без раскрытия секретов и обещаний неподключённых моделей/assets.                         |

Source of truth заданий — серверный job store с owner/principal, deadline, состоянием и ограниченным результатом. Задания переживают создание и закрытие отдельных экземпляров MCP SDK server. Требуются per-owner и глобальные пределы очереди, параллелизма и байтов, TTL, ограничения входа и результата. Абсолютный deadline начинается при принятии задания и включает очередь, загрузку/декодирование, inference и очистку. Отмена остаётся pending до физического завершения owned work; concurrency slot не освобождается раньше. Останавливать/очищать разрешено только ресурсы данного задания или процесса.

Ошибки различают невалидный запрос, запрет доступа, недоступный ресурс, transport/backend/resource failure, отмену/тайм-аут и семантический `unknown` библиотеки. Техническая ошибка сегментации или загрузки не превращается в «объект не найден». Адаптер сохраняет типизированную причину согласно фактическим публичным контрактам библиотеки и не придумывает собственные коды ошибок библиотеки.

### Транспорты, идентичность и входные файлы

- Локальный stdio поддерживает современный MCP и legacy handshake версии протокола 2025 через соответствующие реализации SDK. SSE относится к HTTP-транспорту, а не к stdio. stdout зарезервирован исключительно под MCP frames; диагностика направляется в stderr. Shutdown завершает принадлежащие серверу ресурсы без утечки listeners, timers, потоков или дочерних процессов.
- HTTP поддерживает Streamable HTTP и legacy SSE. Авторизация применяется к каждому запросу. Долгоживущие задания не привязаны к одному созданному на запрос MCP server instance.
- HTTP principal строится из проверенного сочетания OIDC `issuer` и `subject`. OAuth `client_id`, хэш токена, OpenRouter API key и строка, присланная клиентом, не являются идентичностью пользователя задания.
- Resource server валидирует issuer, audience, expiry, scopes и подпись токена, публикует метаданные и поддерживает OAuth Authorization Code с PKCE S256. MCP access token и provider credential — отдельные контуры.
- BYOK onboarding (включая собственный credential flow OpenRouter PKCE, где применим) не превращает provider key в токен MCP. Provider key не передаётся аргументом model tool и не помещается в URL, журналы, ошибки или MCP-ответ.
- Remote HTTP принимает ограниченные private file uploads, URL и/или base64 согласно контракту; для ChatGPT file reference реализуется и проверяется требуемый контракт `download_url`/`file_id`, необязательные `mime_type`/`file_name` и предусмотренный OpenAI `fileParams`. Локальный stdio принимает путь только внутри явно разрешённого root.
- URL-загрузчик защищён от SSRF: проверяются DNS-результат и закреплённый адрес соединения, заново валидируются редиректы и защита от DNS rebinding; ограничиваются редиректы, bytes, тип и время загрузки. Содержимое проверяется и принадлежит серверу до асинхронных операций.
- Задания, файлы и артефакты доступны только их principal и очищаются по TTL. Browser viewer показывает ограниченный JSON, исходные координаты bbox и/или разрешённый cutout с проверкой владельца; он не создаёт впечатление встроенного интерфейса ChatGPT.

Артефакты и сырые свидетельства хранятся вне репозитория под `/root/.codex/artifacts/zorya-classifier-mcp-20261101/mcp-build-v1/`. Выходной шлюз волны 1 пройден: контрактные интерфейсы приняты, но это не означает готовность полного MCP-пакета.

   **Простыми словами:** итоговый пакет проверяется как установленный продукт и серверный протокол, а не только как набор отдельных модулей.

6. **Волна 6 — свежий read-only независимый аудит Luna и финальный аудит главного оркестратора.** После заморозки tree новый независимый аудитор `gpt-6-luna/high/fork_turns=none`, не участвовавший в реализации, получает полный актуальный набор планов и доказательств. Ему запрещено менять implementation/docs; он выносит точное решение `APPROVE` или `CHANGES_REQUIRED` по полному текущему объёму MCP. Во время аудита других изменений нет. Любой substantive fix возвращает работу к интеграционным gates и требует нового свежего аудита. Артефакт — read-only audit receipt во внешнем evidence-каталоге. Exit gate: `APPROVE` по каждому применимому пункту полной MCP-матрицы, без нерешённых MCP `FAIL`, `MISSING`, `UNVERIFIED`, плюс финальная проверка главным оркестратором. H8a не включается в MCP quality gate и остаётся отдельной задачей. Результат: свежий read-only аудитор выдал `APPROVE` по software acceptance 19 требований, root gates и CI; отчёт и SHA приведены в [документе проверки](mcp-validation.ru.md). Из software gates остаются только публикация MCP и проверка registry bytes.

   **Простыми словами:** независимая проверка полного software-результата завершена. Публикация ждёт завершения проверки личности владельца в npm; H8a по-прежнему не оценивался.

### Отдельные проверки развёртывания

Ручной пользовательский сценарий в конкретном аккаунте ChatGPT и production deployment не являются gate готовности исходного кода или npm-пакета. Эти проверки не выполнялись и не подтверждаются тестами SDK; при соответствующем развёртывании нужны отдельные receipts с прямым свидетельством. Это разграничение не ослабляет обязательные проверки MCP tools, OAuth/PKCE, транспортов, клиентских протоколов, безопасности, архива и Docker из матрицы выше.

## Связь с H8a и сохранение свидетельств

`docs/research/v03-h8a-cpu-mcp-plan.ru.md` сохраняет хронологию и receipts CPU-выполнимости, DEV40 и исторических остановов. Его старый порядок, где MCP ожидал независимый H8a quality gate, заменён решением владельца: MCP выполняется сейчас поверх библиотеки `0.2.3`, H8a продолжается отдельно. Это изменение порядка не редактирует исторические данные.

CPU-скрининг 12 строк и 372 корректно упакованных масок измерял техническое завершение, не точность. DEV40 v2 остановился до запросов к модели из-за состава источников; качество H8a там также не измерялось. DEV40/QUAL120 и требования к выбору и независимой квалификации остаются применимыми к отдельному promotion H8a, но не являются входом, зависимостью или gate MCP. Не запускать H8a inference, менять исторические дедлайны/бюджеты либо использовать раскрытые heldout результаты для выбора кандидата в рамках MCP.

Итоговый MCP аудитор явно указывает, что H8a и утверждение об улучшении точности не входят в MCP-проверку. Это исключение не означает `PASS` H8a и не закрывает H8a. Изменение публичной библиотеки или provider behavior требует отдельной проверки совместимости и gates библиотеки.
