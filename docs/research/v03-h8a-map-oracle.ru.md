# Гипотеза и план preflight FreeCol

## Гипотеза

В установленном FreeCol 1.1.0 можно получить независимую метаинформацию о текущем окне карты, не меняя его отрисовку: через собственный клиентский `FreeColFrame` и `SwingGUI` прочитать живые `Game`/`Map`/`Unit` объекты, текущие границы и масштаб `MapViewer`, экранное преобразование тайла и фактический alpha-контур штатного спрайта. Это может подтвердить источник состояния и геометрию кандидатов. Само по себе это не доказывает видимость экземпляра: перекрытые, анимируемые, частично отсечённые или закрытые интерфейсом случаи должны оставаться неопределёнными.

Первый bounded запуск подтвердил локальное соединение и вход в новую одиночную игру, но закончился до карты: `ConnectController.login` показал штатный `StartGamePanel`, а диагностический launcher не выполнил его нормальное действие `start`. Кроме того, процесс namespace-init подтвердил выход своего непосредственного worker, но не перепроверил всех усыновлённых потомков. Следующая проверка исправит только диагностический переход UI и учёт жизненного цикла процессов; до карты это ещё не доказательство работы геометрического наблюдателя.

## Реализация

Добавить изолированный read-only probe в `benchmarks/v03/fresh-dev-map/freecol/`: он запускает только установленную игру из отдельного приватного профиля/домашнего каталога, с фиксированными параметрами и без внешней сети, ограничивает время и вывод, а затем сохраняет JSON-метаданные состояния вне репозитория. Внешний launcher до компиляции копирует точный source/test closure в новый эксклюзивный snapshot, записывает SHA-256 и запускает compile/worker из этих байтов. Он создаёт user, mount, network и PID namespace; PID 1 через `waitpid(-1, WNOHANG)` сохраняет точный статус прямого session-worker и дожидается reaping всех потомков. Worker включает только loopback, запускает Xvfb через динамический `-displayfd` с ограниченным readiness, D-Bus и FreeCol. Внутри mount namespace `/tmp` заменяется приватным tmpfs для X сокетов/lock-файлов. Java probe компилируется против установленного `/usr/share/java/FreeCol-1.1.0.jar`; источник upstream не vendored. Каталоги запуска создаются эксклюзивно. Private profile удаляется только после подтверждённого закрытия namespace и drain pipes; bounded FreeCol log tail сохраняется до удаления. Неизвестное закрытие сохраняет private profile и даёт ошибку, а не успех.

Диагностический UI-переход отделён от oracle: на EDT probe может один раз вызвать обычное `doClick(0)` только у реального `StartGamePanel.start`, если найден ровно один показываемый и доступный panel с соответствующей показываемой и доступной кнопкой. Запись фиксирует идентичность panel/button, состояние и факт доставки штатного ActionEvent. При таймауте сохраняются ограниченные списки видимых блокирующих панелей и кнопок. Никаких прямых изменений модели, генератора карты или отрисовки нет.

Наблюдатель работает после старта клиента и только читает состояние на Swing EDT. Он перебирает все фактические `Map.getTile(x,y)` клетки с жёстким лимитом; для front sprite использует штатное `MapViewerBounds.tileToPoint(tile)` и `MapViewerState.findUnitInFront(tile)`, чтобы учитывать крупный sprite соседнего offscreen-тайла, alpha которого попадает в viewport. Связанный tile unit должен присутствовать в своём `Tile.getUnitList()`; cargo не считается front unit. Установленный bytecode `Map.getUnitList()` здесь не используется: он возвращает пустой список. Полный client inventory требует обхода всех клеток, отсутствия переполнения лимитов, полноты каждого hit-test и отсутствия пересекающего viewport sprite, который анимируется. Учитываются все unit-image alpha bounds, включая spill-in; их сумма и пересечения с HUD/chip проверяются отдельно. Запись включает hashes jar/probe, viewport, camera/focus/scale, sprite resource/alpha/owner/tile, точный renderer front-unit inventory, overlays и видимые UI-панели. Это source-geometry evidence, не screenshot и не pixel-level mask.

Официальный save создаётся штатным `InGameController.saveGame(File)`/`FreeColServer.saveGame`, а загрузки идут отдельными процессами через установленный CLI `--load-savegame`. Хеш фиксированных save-bytes проверяется до/после. Bounded reader проверяет полный dynamic `<unit id="unit:…" unitType="…">` inventory официального `savegame.xml`, включая location и owner; client map unit identities/types/owners сверяются с ним. Это сильнее, чем client fog-tiles: отсутствие valid unit type во всём сериализованном server game можно подтвердить независимо от неизвестной игроку географии. Ограничение: такой факт относится к конкретному снимку мира FreeCol и не является общим утверждением о типе/семантике изображения. Для negative capture дополнительно обязателен нулевой тип в полном all-map tile inventory и полном viewport front-sprite inventory, который считает offscreen spill-in.

## Быстрые проверки

- Fixture tests проверяют отказ при broad/reused path, неизменность снапшота исходников, удаление только маркированного private-профиля, сохранность соседнего sentinel, корректное reaping direct worker и orphan-потомка, timeout/fast-exit cleanup и жёсткий предел log bytes.
- Runtime launcher ограничивает app stdout/stderr двумя мегабайтами, control output 16 KiB, wall-clock временем, readiness Xvfb, JVM-наблюдателем, числом map cells/front-sprite rows и FreeCol log tail. До первого live run JSON schema оставалась неподтверждённой; последующие реальные metadata/capture receipts теперь дают её runtime-пример.
- Скомпилировать probe против фактически установленного jar и закрепить SHA-256 jar/class files в receipts.
- Первоначальный план предусматривал единственный metadata-only запуск `luna-freecol-live-v2` в закрытом сетевом namespace, с private XDG/JVM preferences. Он подтвердил UI-переход, живой источник геометрии и учёт процессов; позднее отдельная фиксированная DEV-диагностика создала снимки, описанные в итоговом разделе ниже.

## Ограничения и критерий продолжения первоначального preflight

Fixture tests доказывают только защитные свойства launcher и сериализатора; компиляция подтверждает совместимость с локальными class signatures. Единственный live metadata run может подтвердить переход к игре, базовую геометрию, факт наблюдения хотя бы одного front sprite и завершение принадлежащего namespace дерева процессов. Он не является оценкой точности сегментации и не даёт corpus-case истины без независимого подтверждения видимой alpha-области и отсутствия перекрытия. Даже inventory экрана остаётся потенциально неполным из-за offscreen tile с крупным sprite. Никакие игровые слоты не допускаются к корпусу, пока владелец не проверит live receipt, целевые состояния, полноту viewport inventory, sprite/resource licenses и честное правило отказа при неоднозначности.

## Результат `luna-freecol-live-v2`

Один запуск завершился за 6,786 с с `namespace-exited`, кодом worker 0, подтверждённым закрытием app/Xvfb групп, reaping двух усыновлённых потомков, закрытым pipe drain и удалённым только private profile. UI-наблюдатель нашёл ровно одну показываемую и доступную реальную `StartGamePanel` и `FreeColButton` `Start Game`, вызвал обычный `doClick(0)` ровно один раз и наблюдал ActionEvent. Карта наблюдалась: 40×100 клеток полностью просканированы; 216 строгих видимых клеток; один front unit и один sprite, пересекающий viewport 1024×737, без анимируемого front unit. Это подтверждает осуществимость источника метаданных и базовой геометрии для этого запуска.

Этот результат не подтверждает точность маски видимого объекта, отсутствие перекрытия/occlusion, полноту всего кадра, отрицательную семантику или качество модели. `visibilityVerdict` остаётся `not-established`, `completeVisibleNegativeInventory=false`; screenshot и corpus case не создавались. Полные неизменяемые source snapshot hashes и receipts находятся снаружи репозитория под `fresh-map/luna-freecol-live-v2/`. Первичный receipt сохранён без правок; отдельный `receipt-field-correction.json` исправляет только ошибочно вычисленное поле `compiledFromSnapshot` (launcher фактически передал snapshot в `compile_agent`).

Перед любым использованием данных основной поток должен независимо проверить source/geometry receipt, смысл alpha bounds и правила консервативного отказа. Даже после такой проверки живой запуск остаётся технической проверкой источника, а не принятым corpus-case.

## Следующая DEV-фаза: пять фиксированных seed-рецептов

### Проверяемая гипотеза и предел

Пять заранее выбранных seed запускаются однократно только для создания официального save; затем четыре состояния назначаются положительными с merchantman, одно отрицательным с valid Flying Dutchman type, отсутствующим в полном server save. Query/label/case ordering фиксируются до любого screen capture и model outcome. Для положительных состояний target выбирается по реальному unit ID/type/owner/tile и полному source/renderer metadata; для отрицательного типа отсутствие проверяется по official server-world inventory, всем client tile units и renderer-front inventory viewport. Кадр захватывается только после замороженной lineup и совпадения state signature. Это проверяет пригодность ограниченного DEV-набора; не проверяет качество модели, accuracy, универсальность игрового oracle или приемлемость будущей разметки для heldout.

### Перепланирование после проверки воспроизводимости

Два независимых запуска с одним и тем же seed `20261101` и одинаковым source closure (`94029951faaf566d7c13d9d0d9888e0aac6b26c46c9356c144dccd291aa87055`) дали разные карты и позиции фокуса. Поэтому seed не считается рецептом точного состояния и metadata-only повтор генерации не используется как proof. Проверена новая гипотеза: официальный `InGameController.saveGame(File)` → `FreeColServer.saveGame(...)` сохраняет реально сгенерированный новый мир, а штатный `--load-savegame` восстанавливает ту же карту/unit/viewport в двух независимых клиентских процессах. Probe вызывает только штатный сериализатор на EDT с уникальным внешним путём; он не пишет модель напрямую и не меняет рендерер. Пять заранее перечисленных seed каждый запускаются ровно один раз для создания состояния и save; зафиксированные bytes и две независимые полные reload-подписи становятся recipe точного состояния.

Проверены пять official saves и по два независимых reload каждого; frozen save SHA остаётся неизменным, state signature/tile+unit digests/target ID/owner/tile/camera совпадают, а client map-unit inventory сходится с полной server-save inventory. Клиентская туманная карта содержит множество unknown `Tile.getType()`, поэтому отрицательный type-check опирается на полный server save, дополнительно проверяется по all-map client tile units и полному render-front inventory с spill-in. Эти проверки доказывают точное воспроизводимое source state, но не pixel-unoccluded box и не качество классификации.

### Предварительно фиксированный lineup

До осмотра любых результатов фиксируются ровно пять seed-рецептов и порядок:

1. `fc-dev-state-01`, seed `20261101` — single-player, штатная кнопка Start Game, карта `40×100` ожидается только как характеристика этого установленного генератора, а не как условие принятия.
2. `fc-dev-state-02`, seed `20261102` — тот же UI-рецепт и приватный профиль.
3. `fc-dev-state-03`, seed `20261103` — тот же UI-рецепт и приватный профиль.
4. `fc-dev-state-04`, seed `20261104` — тот же UI-рецепт и приватный профиль.
5. `fc-dev-state-05`, seed `20261105` — тот же UI-рецепт и приватный профиль.

Каждый seed порождает ровно один официальный save через штатный серверный API; далее два независимых load-процесса должны воспроизвести точные unit IDs/types/owners/tile coordinates, all-map unit inventory digest, map tile-state digest, focus, scale, viewport, UI action, target resource key и geometry. Перед фиксацией lineup каждый metadata load обязан иметь три последовательных одинаковых EDT signature, чтобы временный viewport/layout startup не считался стабильным. Состояния с одним terrain digest объявляются одним визуальным scene-group; их нельзя представлять как независимые изображения, даже если серверная identity/save отличается. Этот конечный roster не пополняется по результатам model outcomes; неоднозначный или невоспроизводимый слот остаётся исключённым и блокирует нужное число DEV-case.

Запуск использует ровно один normal `doClick(0)` на показанной и доступной настоящей `StartGamePanel.start`. Если на EDT показан один FreeCol `InformationPanel`, его настоящий enabled `FreeColPanel.okButton` (`actionCommand=OK`) может быть вызван обычным `doClick(0)` один раз: установленный bytecode `FreeColPanel.actionPerformed` удаляет этот UI-компонент через `GUI.removeComponent`. Это только закрывает foreground modal UI, не меняет карту/юниты. Любой иной или неоднозначный блокирующий компонент не нажимается вслепую; он блокирует state и capture.

После пяти official-save и десяти независимых metadata-load runs фиксируется упорядоченный `lineup-freeze.json`: source closures/jar hashes, пары load run IDs, frozen save hashes, подпись состояния, exact target type/query, label, unit/owner/tile либо global-absence proof, viewport/scale, ResourceManager key/locator/hash, license evidence, сцено-группа и критерий окклюзии. Только после физической записи и хеша этого freeze разрешены ровно пять новых capture runs, которые загружают pinned `.fsg` bytes; screen image создаётся один раз через Robot с реального клиента. До freeze нет screenshot, crop, mask PNG, image-model request, candidate ranking или model outcomes.

### Критерии допуска и безопасный отказ

- Глобальная инвентаризация сканирует каждую ненулевую tile и её реальный `getUnitList()`, не cargo; любой cell/row cap, ошибка tile или неоднозначный unit state запрещают negative proof. Выбранный отрицательный type должен существовать в FreeCol `Specification`, но быть полностью отсутствующим во всех этих tile lists.
- Положительный target — ровно один настоящий renderer front unit с валидным unit ID/type/owner/tile, неподвижная анимация, непустой ImageLibrary sprite/alpha и положительное пересечение его экранной области с viewport. Позиции для всех tile вычисляются реальным `tileToPoint`; это также проверяет offscreen spill-in. ID и anchor сохраняются из реального engine state, не из screenshot.
- Геометрия не превращает tile в объектный bbox. Для каждой положительной сцены фиксируются renderer sprite offset/масштаб, исходный tile anchor, alpha bounds и pixel hash. Отдельно проверяются фактический `ImageResource` key/locator, альтернативы/вариант scale и установленный copyright/license. Неизвестный alias, источник или разрешение — veto.
- Рендерер FreeCol добавляет occupation/nation chip, stack lines и health bar; UI может перекрыть карту. Screenshot capture дополнительно сравнивает каждый fully-opaque RGB-пиксель исходного sprite с теми же координатами полного Robot-снимка, отдельно на chip overlap. Если chip точно закрашивает target pixels, unoccluded-positive gate провален даже когда край bbox остаётся видимым; можно сообщить только box-only visibility. Совпадение alpha extent с настоящим screenshot фиксирует именно observed pixels, а не подменяет ручной осмотр. Последующая capture — полный неизменённый экран реального GUI, не повторная отрисовка/подмена.
- Отрицательный кадр воспроизводит frozen `.fsg`; type должен быть валиден по Specification, absent в полном authoritative server save, absent во всех client map tiles и absent в полном viewport front-sprite inventory, включающем offscreen spill-in. Отрицательный не строится на «не нашёл в видимых клетках». Положительные и отрицательный слот могут иметь разные конкретные type queries; lineup фиксирует текст каждого запроса заранее до screenshot.
- Capture fixture проверить на синтетических UI/component bounds и побочных файлах, а не считать это доказательством FreeCol pixels. После freeze — только реальные screen captures из приложения в приватном namespace и подтверждённые изображения; нет synthetic renderer, screenshot editing, API/model traffic или corpus publication.

Зафиксированный roster остался неизменным: четыре положительных merchantman case (`fc-dev-case-01`..`04`) и один отрицательный Flying Dutchman case (`fc-dev-case-05`). Каждое состояние создано штатным API, дважды независимо загружено с одинаковой signature, а последние metadata receipts также имеют одинаковую стабильную геометрию 1024×737. Merchantman resource key/path/hash совпадает с реально выбранной базовой картинкой; Debian package evidence объявляет выбранный ресурс GPL-2+. Четыре положительных случая относятся к одному unit type/sprite family. Состояния `04` и `05` имеют одинаковый `mapTileStateSha256` и остаются одной группой близких игровых сцен; полноэкранные PNG не идентичны. Во всех пяти server save inventories Flying Dutchman count равен нулю при наличии type в Specification; client tile map и complete viewport front inventory проверяются дополнительно.

Непрозрачные пиксели merchantman пересекаются с occupation chip: source renderer analysis предсказывает 221 закрытый пиксель, хотя край alpha bbox остаётся неизменным. Это не unoccluded-positive admission. После capture главный оркестратор визуально проверил все пять полноэкранных PNG и исходный pinned sprite. В каждом положительном кадре chip закрывает часть корабля; bytecode `MapViewer.displayUnit` подтверждает порядок: `drawImage(sprite)` на offset 78, затем `drawImage(occupationChip)` на offset 116 (`main-freecol-mapviewer-bytecode-v2.txt`, строки 2275–2337). Все четыре положительных кадра поэтому отклонены для unoccluded-positive требования. RGB реального рендеринга отличается от исходного sprite и за пределами chip, поэтому не заявляется pixel-exact alpha extent или что все отличия вызваны только chip. Геометрический alpha bbox остаётся диагностикой источника, не доказанным точным bbox видимого объекта.

### Первый зафиксированный capture gate и точечное исправление

После физической фиксации v1 lineup были запущены ровно пять заранее перечисленных capture-команд с pinned save bytes. Все пять завершились с `capture-veto-incomplete-or-blocked-state` до PNG: renderer/map inventories были полны, но общий счётчик `visibleFreeColPanelCount=1` ошибочно запрещал постоянный правый `InfoPanel`. Ни screenshot, ни pixel comparison в этих пяти запусках не возникли; все v1 run receipts и неуспешные результаты сохранены. Для v2 gate различает один известный persistent `InfoPanel` и transient/unknown `FreeColPanel`: разрешается не более одного именно этого класса только при полном inventory всех видимых компонентов и screen bounds; любое иное видимое FreeColPanel, внешнее окно, неполный компонентный inventory, неизвестные bounds или пересечение target с HUD veto. UI не скрывается и не перемещается.

Fixture gate проверяет непересекающуюся панель, пересечение с target, неизвестный dialog, внешнее окно, неполный inventory, неизвестные bounds и неоднозначный повтор класса. V2 использует отдельные metadata run IDs/source closure и внешний append-only capture-gate receipt, ссылающийся на неизменный v1 manifest digest; он не заменяет и не удаляет v1 evidence и не меняет query/state/case order.

## Итог завершённого V2 capture roster

После первого v1 отказа gate был ограниченно исправлен: разрешается только один известный постоянный `net.sf.freecol.client.gui.panel.InfoPanel`, если полный видимый component inventory и все screen bounds доступны, а target не пересекает панель. Неизвестный/transient panel, внешнее окно, неполный inventory, неизвестная геометрия или пересечение target по-прежнему блокируют capture.
