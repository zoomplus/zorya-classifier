# Проспективный replay с диагностикой отказов поставщика

**Статус:** отдельная экспериментальная политика описана и реализована в benchmark-коде, но новое исследование пока не зарегистрировано и не запускалось. 83 сфокусированных теста, typecheck, lint и форматирование прошли. Общая проверка `npm run check` и проверка установленного архива выполняются отдельным интеграционным этапом. Это не результат проверки поставщика и не объяснение прежней ошибки Camera.

## Что проверяет политика

Запечатанный DEV40 завершился после 15 из 40 полных пар. В контрольном вызове Camera наблюдался HTTP 502, но текст ответа не сохранился; причину нельзя восстановить или переоценить задним числом. Предыдущий отчёт сохраняет этот результат и его ограничения ([DEV40](./v03-h8a-ui-state-dev40-results.ru.md)). Проспективная гипотеза — отдельно наблюдать только явно сообщённый отказ, если его можно привязать к фактическому запросу. [Руководство OpenAI Decisions](https://developers.openai.com/api/docs/guides/decisions) описывает типизированный отказ; сообщение автора [Hindsight issue #6242](https://github.com/vectorize-io/hindsight/issues/6242) касается стороннего маршрута OpenRouter System One (`/api/v1/systemone`) и не доказывает причину Camera на `/api/alpha/decisions`.

Политика необязательна в замороженной конфигурации. Если `executionPolicy` отсутствует, действует прежний путь; старые API и записи не меняются. Для opt-in зафиксированы идентификаторы:

```json
{
  "schema": "h8a-provider-refusal-replay-policy-v1",
  "policyId": "h8a-provider-reported-refusal-replay-v1",
  "hypothesisSha256": "c4ccc40c47b8341a5ea2445b71733d64a5ca8fe8111c7343d1099ebf707d950b",
  "observationProtocols": [
    "openrouter-native-named-refusal-v1",
    "openrouter-chat-message-refusal-v1"
  ],
  "policySha256": "ba0684f8f475a32af5a9369ff5f2d67c55e612fde2ddf2ab4be441eadfe89692"
}
```

Распознаватель принимает только два вида связанного с запросом наблюдения. Для native Decisions это один типизированный ответ HTTP 200 с `type: refusal` и именем вопроса, который действительно присутствовал в отправленном запросе, либо строгое тело ошибки HTTP 502 с точным отказом отвечать на такой запрошенный ID. Для chat допустим только HTTP 200 с зафиксированным recorder признаком `chat-refusal` и непустым фактическим `message.refusal`. В обоих случаях проверяются POST на точном URL/маршруте, профиль, модель и поставщик, настройки маршрутизации без fallback, хэши тела и запроса, ID физического вызова и связность записей. Если ответ содержит модель или поставщика, они тоже должны соответствовать маршруту. Поддерживаются текущие маршруты H8a chat (`openai/gpt-6-luna`, `/api/v1/chat/completions`) и native-контроля (`openai/gpt-6-luna-decisions`, `/api/alpha/decisions`); этот контроль не является отдельным историческим исследованием Jev native-box. Это зафиксированные маршруты данного исследования, а не значения по умолчанию библиотеки.

## Результат и границы

Распознанный отказ сохраняется как исходный HTTP/ошибка и неуспешная логическая запись, вместе с подтверждённым физическим dispatch и известной стоимостью либо неизвестной суммой. В исследовательской строке он может дать `unknown`, но без box, mask или cutout. Положительный пример при этом остаётся пропуском; `unknown` на отрицательном примере не доказывает отсутствие объекта. Политика не создаёт оценки, ответа, геометрии или частичного успеха.

Общий 502, похожая формулировка, чужой или отсутствующий ID, другой маршрут/модель/поставщик и native-массив с отказом, смешанным с другими ответами, не распознаются этой политикой. Обычные успешные native-ответы с несколькими вопросами остаются поддержанными. Отмена, неопределённый или незавершённый dispatch, ошибка записи артефактов, persistence или native/cleanup остаются техническими исходами и блокируют продолжение. Повторов и fallback нет. Неизвестная сумма не превращается в нулевую: сохраняется консервативный резерв и показывается диапазон затрат. Корень временных файлов принадлежит вызывающему процессу; новая CLI должна создавать для запуска отдельный каталог и удалять его после завершения физической работы. Ошибка очистки отдельного каталога случая остаётся технической ошибкой.

Replay использует те же раскрытые 40 DEV-источников, слова целей, профили, расписание, лимиты и пороги. Это повторное исследование тех же данных, а не новая независимая выборка; ответы и маски старого запуска не переиспользуются. Лимиты остаются 4 физических вызова на случай кандидата и 6 на контроль. Для DEV нужны все 40 полных пар, ноль ложных выходов на 10 отрицательных случаях и существующая проверка nested-screen. Только после полного DEV возможно отдельно собирать независимые 120 случаев QUAL: не менее 54/90 положительных успехов, 12/30 в каждой страте, прирост не менее 20 п.п., нижняя кластерная граница 95% выше нуля, не более 1/30 ложных выходов и не менее 15/30 масок с IoU ≥ 0,8. Неудачный QUAL не используется для подбора нового кандидата.

Текущие 202 физических вызова и `$0.118405065` известной стоимости относятся к предыдущим исполнениям; резерв `$0.24` остаётся неизвестной суммой, а не подтверждённым расходом или возвратом. В этой волне не было новых provider-вызовов, replay-регистрации, QUAL, реализации MCP или публикации. Изменение относится только к benchmark-диагностике и не меняет публичную семантику библиотеки.
