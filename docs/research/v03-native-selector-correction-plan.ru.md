# План исправленного DEV-сравнения H8a native-selector

**Статус на 2026-11-02:** отдельное исправленное DEV-сравнение спроектировано; этот документ не регистрирует исследование и не разрешает вызовы провайдера или native inference. Первый запуск `native-selector-flat-dev40-v1` завершён со статусом `STOP`, остаётся неизменяемым и непригодным для квалификации. Его частичные результаты нельзя переносить, переименовывать или повторно учитывать в новом исследовании.

## Причина отдельного исправленного запуска

Исходный запуск остановился на 15 из 40 пар: 24 пары не начинались, ещё одна осталась частичной. В запросе выбора было наблюдено точное именованное решение провайдера об отказе с HTTP 502. Историческая копия адаптера создала `ClassifierError` с кодом `PROVIDER`, однако рекордер сравнивал экземпляр по идентичности класса, загруженного из другой копии модуля, и записывал `PROVIDER_ERROR`. Из-за этого строгая уже замороженная политика отказов не могла связать наблюдение с техническим исходом `unknown`.

Исправление рекордера сохраняет только известные коды закрытого набора `ErrorCode` для структурно проверенного `Error`; оно не интерпретирует текст ошибки, не принимает произвольные коды и не расширяет политику семантического отказа. Регрессии с контролируемым `fetch` проверяют совместимость копий класса и сохранение исходного строгого правила. Тексты запросов, решения, оценки, разметка, пороги и метрики не меняются. Это исправление дефекта реализации, а не новая гипотеза и не подбор результата по уже увиденным исходам.

## Идентичность и неизменяемые границы

Исправленное исследование использует новые закрытые идентификаторы: `native-selector-flat-dev40-corrected-v1`, freeze `h8a-native-selector-flat-dev40-corrected-20261102-v1` и отдельный канонический корень `native-selector-flat-dev40-corrected-v1`. Фаза, профиль, рецепт, запросная политика, политика присутствия, политика выбора, порядок полей, маски, source cases, paired schedule и критерии остаются прежними. Candidate и control сохраняют свои самостоятельные policy bytes и хеши. Старые профили и receipts не переписываются.

Новый parent audit связывает точные bytes протокола, freeze, источников, разметки, ledger, регистрации, closeouts, reports и физических/логических receipts с завершённым, но остановленным V5 parent. Состояние parent переносится фактически: 413 физических dispatch, 134 попытки case-arm, `$0.22744121499999995` известной стоимости, `$0.36` резерва неизвестной стоимости и следующий physical/reservation ID `414`. Унаследованный STOP остаётся причиной для отдельного исправления и не снимается задним числом.

## Бюджет и время

Глобальный предел составляет 2000 физических вызовов, включая подтверждённые, неопределённые и ожидающие dispatch. Исправленному DEV выделяется не более 400 новых вызовов и `$48` резерва по `$0.12` на dispatch; лимиты на case — 4 для candidate и 6 для control, повторов и fallback нет. Общий абсолютный дедлайн `2026-11-02T12:11:51.738Z` и таймаут case 240 секунд сохраняются; истёкший дедлайн нельзя продлевать этой правкой.

QUAL на 1200 вызовов и `$144` остаётся условным и этим этапом не резервируется. Новое DEV может использовать исходный предел 400; если после фактического расхода доступного глобального бюджета останется меньше 1200 вызовов, будущий QUAL admission обязан отказать до чтения ключа, создания runtime или первого fetch. Для полного 1200 QUAL фактический расход исправленного DEV должен оставить глобальный остаток не меньше 1200; при исходном parent это означает не более 387 новых DEV dispatch. Нельзя объявлять, что полные лимиты 400 DEV и 1200 QUAL одновременно помещаются в глобальные 2000.

## Этапы и проверки

1. **Исправленный план и отдельная запись статуса.** Зафиксировать причину дефекта, новую идентичность, сохранённые методику и бюджет, границы старого STOP и будущие независимые проверки. Это помогает отличать исправление рекордера от изменения эксперимента.
2. **Изолированная реализация replay lifecycle.** Добавить закрытый registry entry и явный CLI для исправленного study; валидировать точную цепочку parent audit → protocol/freeze → registration/ledger → closeouts/reports/receipts. Создать раздельные caches, launch intents, terminal STOP и ledger, наследующий ID 414 и реальные counters. Новые изменения не заменяют старые CLI или ретаргет-правила.
3. **Офлайн-регрессии и основной аудит.** На временных fixture roots проверить полный register/run/review/closeout, запреты повторного запуска, несоответствия идентичности, истечение срока, сбои очистки и неизвестную стоимость. Контролируемые fetch-тесты должны пропускать точный именованный отказ через существующую политику к `unknown`, сохраняя generic 502 технической ошибкой. Проверить бюджеты с незавершёнными резервами и отклонение QUAL при недостаточном фактическом остатке. Затем главный оркестратор независимо проверяет diff, запускает полные gates и проверяет установленный архив.
4. **Будущий отдельный запуск.** После интеграции потребуется новая freeze с source closure, содержащим исправленный CLI, QUAL lifecycle и этот план; затем независимая проверка hash/AST/runtime/цены/источников/бюджета и отдельная регистрация. Запуск DEV выполняется только отдельной командой и review-gates DEV8 → DEV12 → DEV40. Этот этап W37 не создаёт новый study root, protocol, registration и не запускает inference.
5. **Будущая квалификация.** QUAL допускается только после завершённого исправленного DEV, полного покрытия и review-gates, отсутствия ложных выходов и проверки фактически оставшегося глобального бюджета не менее 1200. Текущий остановленный parent, fixture-проверки и программные gates не заменяют такую квалификацию.

Для будущих контролируемых UI/map источников план дополнен закрытым методом `independent-source-oracle-v1`: он должен связывать конкретный case, исходные bytes и canvas, target text, группу, ожидание наличия и геометрию с закреплёнными raw source-state, полным видимым инвентарём, transform и кодом model-free oracle. Этот метод недоступен для фото; независимые 30 фотомасок продолжают требовать ранее разрешённое человеческое или опубликованное ground truth. Proof остаётся частным для evaluator и не передаётся producer. До открытия QUAL Main отдельно проверяет исходные captures, screenshots и полноту inventory: schema и file hashes фиксируют bytes, но сами не доказывают правдивость source oracle. В W37 не приобретаются и не открываются реальные QUAL-источники.

Исправленный QUAL также обязан сохранять обе части исторического исключения, связанные через pinned parent source-audit → preparation: 440 исторических source groups и 348 fingerprint-записей. У pixel-записей доступны encoded SHA, Pillow RGB SHA и pHash, но нет Sharp RGB, case ID или source group; эти отсутствующие связи и хеши не выводятся и не выдумываются. Проверка до чтения credentials, создания runtime и fetch сверяет точные pinned refs и commitments, объединяет группы и доступные fingerprints с явными строками исключения и запрещает опустить любой из двух исторических блоков. Для прежней QUAL-ветки без этого блока остаётся прежний явный row-only контракт.

## Область реализации

Кодовая работа ограничена отдельной веткой `benchmarks/v03/h8a-fresh-comparison/`, её явным CLI и портативными regression tests с отдельными catalog entries, плюс этим документом и краткой записью в `docs/0.3.0-quality-plan.md`. В частности, правки не меняют публичные API, профили, prompts, native implementation, `recording.ts`, package version, существующие hash алгоритмы, существующие frozen records или исходную гипотезу. Все офлайн-проверки используют временные namespaces и контролируемые зависимости; они не доказывают качество локализации и не разрешают сетевой, оплачиваемый или квалификационный запуск.
