# v0.3 офлайн color-normalization v1 (HSV12)

Проверили один вариант идеи: каждый пиксель заменяется одним из 12 цветовых тонов либо чёрным, серым или белым. Размер изображения и координаты не меняются. Затем находятся соприкасающиеся пиксели одинакового цвета, а их маски накладываются на оригинал. Ниже — зафиксированные числа, ограничения интерпретации и ссылки на артефакты; это не поведение production-библиотеки.

Ретроспективное сравнение методов на том же DEV12-пилоте и выбор **`color-normalization-hsv12-v1` как текущего экспериментального опорного профиля** (не runtime-дефолт, не лучший E2E): [v03-method-comparison.ru.md](./v03-method-comparison.ru.md). Канонический HTML-отчёт: `/root/.codex/artifacts/zorya-classifier-method-comparison-20261025/report-final/comparison.html`.

**Что означают главные цифры (простыми словами):** на девяти **положительных** строках задач (объект в кадре по **эталонной разметке**) оценщик ищет **связную цветовую область**, которая одновременно даёт пересечение эталонной рамки и рамки области по IoU ≥ 0,5 и покрытие эталонной рамки ≥ 0,9. HSV12 нашёл такую область в **4 из 9** строк, контроль exact RGB — в **2 из 9**. Это ответ «есть ли подходящий **кандидат** при известной разметке», а не автоматическое распознавание без эталона. Для единственной эталонной **маски** (птица) лучшее пересечение масок IoU у HSV12 ≈ **0,516** — заметно выше контроля (~0,002), но порог **0,8** не достигнут: часть тела попала в одну компоненту, но к ней присоединилась ветка близкого оттенка, а участки другого цвета не вошли. Нормализация в 12 тонов **сильно снижает** число мелких областей и **соседних пар пикселей разных цветов**, но **может склеить** соприкасающиеся участки одного оттенка и **не склеить** части одного объекта, если оттенки разошлись.

**Ограничения по кейсам:** успех порога для рамок на photo-01 **не** означает центральный серый автомобиль — маска вырезанного объекта c1137 покрывает частичный жёлтый слева. Отрицательные строки (3) — только геометрия компонент; ложные срабатывания **не измерялись**.

## Метод (зафиксирован до прогона)

Сравнивается профиль **HSV12 + black/gray/white** с **контролем** исходного RGB без изменений при том же альфа-канале и 4-связности. Семантические предположения, игровые эвристики, модели и вызовы provider **запрещены**. Один полный DEV-прогон, `maxProviderCalls = 0`, без подстройки после результата.

Источники формулировки HSV (не семантика объектов):

- [OpenCV: Color spaces](https://docs.opencv.org/4.12.0/df/d9d/tutorial_py_colorspaces.html)
- [Microsoft: HSV color spaces](https://learn.microsoft.com/en-us/windows/win32/wcs/hsv-color-spaces)

### Фиксированный рецепт нормализации

- Hue bins = 12; `hueBin = floor((hueDegrees + 15) / 30) mod 12`.
- Black: `V < 0.15` → RGB(0,0,0).
- Achromatic: иначе если `S < 0.2`: gray RGB(128,128,128) при `V < 0.75`, white RGB(255,255,255) при `V >= 0.75`.
- Chromatic: центр hue-бина, `S=1`, `V=1`, детерминированное преобразование в 8-bit RGB с `Math.round` на канал.
- Alpha исходного пикселя **сохраняется**; `alpha == 0` исключает пиксель из компонент.
- Без resize/blur/морфологии; координаты — полные EXIF-oriented source pixels.
- Связность: 4-соседняя, `minComponentArea = 1`.

### Карта компонент (portable)

Gzip поверх бинарного блока: magic `ZCNMAP1\0`, profile byte (`1` control / `2` HSV12), width/height uint32 LE, row-major uint32 labels (`0` = фон).

Источник **не** обращается к эталонной разметке. Оценщик использует эталонную разметку **только после** полной валидации завершённого прогона и SHA-256 зафиксированной эталонной разметки.
