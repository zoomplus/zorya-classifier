# Proposal pipeline resource soak receipt

This receipt summarizes the 2026-10-20 Linux CPU run of the public MobileSAM object-proposal workflow. It is a resource and lifecycle measurement for that workflow only; it does not qualify the later region-seeded full-source extraction composition.

The run used Node v24.12.0 on Linux x64, a synthetic 256×256 image, two ONNX threads, one active native child and two queued jobs, a 600-second warmup, 30-second idle windows, 6,540 seconds of alternating locate/extract work, and five-second samples. Forced garbage collection was disabled and the injected decision port made no provider or HTTP calls. The run naturally completed 3,022 operations: 1,511 locates and 1,511 extractions, all successful. It recorded 3,022 child starts and closes, no remaining owned children, and passed abort-and-join, queue/dispose, and parent-loss checks.

Monotonic validation recorded 601,436 ms warmup and 6,600,933 ms measurement (30,000 ms initial idle, 6,540,901 ms busy, and 30,001 ms final idle), for 7,210,991 ms from process start. A separate `/proc` witness observed the same PID and start-tick identity alive at process age 7,210.46 seconds before recording its exit. All 55 pinned source files matched before and after the run.

The idle-window median RSS grew from 327.7 MiB to 556.0 MiB, a 228.3 MiB increase. This exceeds the investigation threshold `max(20% of initial RSS, 128 MiB)` (128 MiB here), so the RSS criterion is **under investigation**, not a resource pass. Over the same windows, heap used changed from 13.8 MiB to 19.5 MiB, external memory from 52.7 MiB to 8.6 MiB, and ArrayBuffers from 1.3 MiB to 5.3 MiB. The parent RSS five-minute median climbed from about 378.9 MiB during minutes 15–20 to 493.3 MiB during minutes 20–25, then rose gradually to about 556 MiB near the end. It was flat within the final idle window (556.4 to 556.0 MiB). These counters do not identify the retained RSS category or establish a leak; native allocator or mapped-memory retention remain possibilities. No forced GC or post-run memory reclamation was used to classify it.

Host snapshots recorded 16 logical CPUs, 33.19 GB physical memory, 27.20 GB then 27.12 GB available memory, 8 GB swap, and about 794.8 GB then 794.3 GB free disk. The run overlapped other development activity, so its operation timings are not suitable for latency ranking. It is retained as an honest historical baseline and does not stand in for the region-seeded workflow.
